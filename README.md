# Icarus

Агент для семьи из 2–5 человек: **хорош в обычном разговоре**, но умеет всё взрослое — читать и править файлы,
искать в интернете, вызывать MCP-инструменты и **помнить**. Входы — Telegram-бот и веб-панель
(`chat.trousev.pro`); OpenAI-совместимый эндпоинт остаётся в сервисе для будущих клиентов и отладки.
Все входы ведут к одной памяти человека.

Устроен как тонкий сервис поверх [pi](https://github.com/earendil-works/pi) — открытого агентского харнесса.
Своего цикла агента мы не пишем: pi живёт в контейнере пользователя, а icarus только превращает разговор
(Telegram, веб-чат, OpenAI-клиент) в живую сессию pi и обратно.

## Как это выглядит

```
Telegram / веб-чат ──► icarus ──docker exec + JSONL──► pi в контейнере человека
                          │                                  │
                          │                                  ├─ персона        (icarus.md)
                          │                                  ├─ ядро памяти    (память всегда под рукой)
                          │                                  ├─ разбор         (факты → полки → git)
                          │                                  ├─ веб-поиск      (web_search, web_fetch)
                          │                                  ├─ субагенты      (subagent: очередь, до 4 разом)
                          │                                  ├─ MCP            (pi-mcp-extension)
                          │                                  ├─ скиллы         (SKILL.md в ~/.pi/agent/skills)
                          │                                  └─ эскалация      (быстро / сильно / зрение)
                          ├─ панель управления (чат: диалоги, картинки, трассировка, файлы workspace; память и скиллы — настройками)
                          └─ OpenAI-совместимый API (/v1) — оставлен для будущих клиентов
```

## Что уже работает

- разговор в Telegram (текст, фото, голосовые), в веб-панели (диалоги, стрим, markdown, картинки)
  и через `POST /v1/chat/completions` со стримом и отменой;
- память между разговорами: ядро в промпте, фоновый разбор после затишья, git-коммит на каждый разбор;
- изоляция: свой контейнер, своя память, свой ключ на человека; общая память — только по явной просьбе;
- workspace'ы: у человека несколько рабочих папок (`/workspaces/<имя>`), каждая со своим `AGENTS.md`;
  служебное — память, сессии, вложения, персона — лежит рядом, в `/workspaces/.icarus`, и ни в одну
  папку не входит. «Приватный» workspace только для чтения: память из него не обновляется;
- вложения из чата: картинки уходят модели нативно, файлы ложатся в `incoming/`;
- веб-поиск и MCP-серверы без правки кода; в панели — раздел **MCP**: человек добавляет
  свой сервер, включает его себе и по желанию делится с остальными;
- **артефакты**: общая библиотека `/artifacts` с папками-артефактами, правами «я/семья» и
  уровнями none/read/write/admin (по умолчанию семейный доступ выключен); у каждого артефакта есть
  внутренняя ссылка в панели, а публичная создаётся по просьбе и открывается с панелью или без неё
  (см. «Артефакты»);
- субагенты: модель раздаёт задачи отдельным процессам pi — со своим контекстом, очередью и
  запретом вложенности; дети возвращают только вывод, а ход ждёт их всех;
- эскалация моделей: болтовня, поиск и чтение — на быстрой, работа руками (bash, правки, MCP) — на сильной, картинки — на зрячей;
- веб-панель (Icarus Control Panel): чат с диалогами, стримом, трассировкой шагов, картинками
  и панелью файлов рабочей папки;
  за SSO-прокси. Память и скиллы открываются настройками поверх чата: смотреть, искать, откатывать
  коммит, забывать строку, удалять файл целиком — и свои скиллы: написать, поправить, удалить,
  вернуть откатом (скиллы тоже под git, а сохранённый скилл доезжает до Икара следующим ходом);
  MCP — отдельным разделом: добавить сервер, включить себе, поделиться и настроить доступ;
  ключи инсталляции правит админ прямо в панели — без `ssh`, правки `.env` руками и пересборки;
- скиллы pi: `SKILL.md` в `~/.pi/agent/skills` человека работает как родной скилл pi — модель видит
  каталог в промпте и читает тело по требованию. Авторство — в панели, синхронизации с внешним чатом нет;
- Telegram: бот отвечает знакомым из `telegram.mapping`, понимает текст, фото и голосовые (картинка
  уезжает модели нативно, голосовое расшифровывает Whisper) — ответ доезжает живыми правками сообщения,
  команды `/compact`, `/stop`, `/stats`, `/clear`, `/rename` и `/skills` бот разбирает сам, не
  отправляя их репликой в модель.
  Час тишины — и Икар сам подводит итог и закрывает сессию pi; следующая реплика поднимает её заново
  по сжатой истории (см. «Сессии и сжатие»).

## Запуск

```bash
# 1. зависимости и локальные конфиги (запускать после clone и после каждого git pull)
./script/update
# он создаст config.yaml из config.example.yaml — поправить людей, модели и пути;
# ключи провайдеров кладутся в .env (образец .env.example, в git не попадает)

# 2. образ контейнера пользователя (./script/server тоже умеет его собирать)
docker build -t icarus-user:dev docker/user/

# 3. стек: ./script/server собирает docker-compose.yml из config.yaml и поднимает его
./script/server                     # icarus на :8081, логи в консоли (Ctrl-C гасит стек)
./script/server -d                  # то же в фоне: переживёт и терминал, и перезагрузку
./script/server --down              # погасить стек

# панель управления — это корень домена (на проде https://chat.trousev.pro/):
# вход обычный, через SSO-прокси, и открывает она память только вошедшего.
# Локально без прокси скажи config.yaml, кем прикинуться: panel.devUser: <id>
```

`./script/server` не запускает процесс, а **собирает `docker-compose.yml`** из `config.yaml`:
сервис icarus и по контейнеру на человека. Сам icarus тоже едет
в контейнере (образ `icarus-service:dev` из `docker/service/`, собирается автоматически).
Жизненным циклом владеет docker, а не сервис: `restart: unless-stopped` возвращает контейнеры
и после падения, и после перезагрузки машины, а смена образа, маунтов или окружения
пересоздаёт их при следующем запуске. Сгенерированный `docker-compose.yml` в git не попадает;
правки в коде доезжают после `docker compose restart icarus` — репозиторий примонтирован.

Порядок запуска выбран ради меньшего простоя при обновлении: сначала `docker compose build`
и сборка образа человека — **пока старые контейнеры ещё работают**, и только потом `up`,
которому остаётся пересоздать изменившееся. Поэтому собирать образ руками (шаг 2) не обязательно:
`./script/server` делает это сам, а `--build` повторяет сборку без кеша.

Первый запуск после перехода со старой схемы: погаси icarus, запущенный обычным процессом на
хосте (`node packages/service/src/index.ts …`) — он держит :8081 и пересоздаёт контейнеры мимо
compose. `./script/server` один раз снесёт контейнеры без метки проекта и поднимет их заново.

## Конфиг

Конфиг — `config.yaml` в корне (образец `config.example.yaml`, рабочий файл в git не попадает):

```yaml
apiKey: icarus-local-token      # Bearer для OpenAI-совместимого эндпоинта (/v1)
# url: https://chat.trousev.pro/     # внешний адрес панели управления: его Икар называет в чате
                                    # (локально по умолчанию http://localhost:8081)
dataDir: ~/icarus-data          # память, сессии и каталоги людей
sessionIdleMinutes: 60          # час тишины: Икар подводит итог и гасит сессию pi

panel:                          # панель управления: кого пускать
  userHeader: Remote-User       # заголовок SSO-прокси, которым он называет вошедшего
  # devUser: probe              # локальный запуск без прокси; на проде не задавать

models:                         # общие модели: tier раздаёт эскалация
  - { provider: deepinfra, id: deepseek-ai/DeepSeek-V4.1-Flash, thinking: off, tier: fast }
# auth: { deepinfra: env:DEEPINFRA_API_KEY }   # обычно не нужно: ключ подхватится из .env
env: { TZ: Europe/Dublin }      # часовой пояс человека: по нему Икар считает дату и датирует память
# кастомных маунтов нет: контейнер видит только /workspaces и установку Maple
mcp: {}                         # общие MCP-серверы; личные и расшаренные — в панели

users:                          # люди: только id
  - probe
  - probe2

# telegram:                     # бот: telegram username → id из users (токен — в .env)
#   mapping:
#     '@trousev': trousev       # в yaml «@» берётся в кавычках: иначе не разберётся
#     '@vita': vita
# speech:                       # голосовые из Telegram: чем расшифровывать (ключ — в .env)
#   language: ru                # по умолчанию Whisper у DeepInfra; `speech: none` — выключить
```

Провайдер `deepinfra` — не встроенный в pi, поэтому его описание (базовый адрес, протокол,
ключ, метаданные моделей) живёт в `packages/service/src/providers.ts` и уезжает в
`models.json` контейнера. В `config.yaml` остаётся только выбор: провайдер, id модели,
уровень размышлений и tier.

Ключи живут в `.env` в корне (образец — `.env.example`, рабочий файл в git не попадает и
создаётся `./script/update`):

```bash
DEEPINFRA_API_KEY=...     # ключ провайдера из models: кроме окружения, попадает в auth.json
TAVILY_API_KEY=...        # ключ веб-поиска: серверного поиска у DeepInfra нет
BRAVE_API_KEY=...         # необязательная альтернатива: ICARUS_SEARCH_PROVIDER=brave
```

Поиск работает и совсем без ключей: у You.com есть бесплатный MCP-профиль без
регистрации — 100 запросов в сутки. Роутер зовёт его сам, как обычного провайдера
(`you-free`); умеет он только искать, для чтения страниц (`web_fetch`) нужен ключ.
Выключить — `ICARUS_SEARCH_FREE=off`.

Ключ провайдера из `models`, для которого в `.env` нашлось значение, подставляется сам:
дублировать его в `config.yaml` не нужно. Блоки `auth:` и `env:` остаются для переопределения
и для провайдеров, которых нет в списке известных (`PROVIDER_ENV` в
`packages/service/src/config.ts`). Окружение сильнее файла: `export DEEPINFRA_API_KEY=…`
перебьёт строку в `.env`. После правки `.env` хватит `./script/server` — compose пересоздаст
контейнеры; сами значения в `docker-compose.yml` не пишутся, туда едет только путь к файлу.

### Ключи в панели

Раздел **«Ключи»** (`/panel/keys`) правит те же секреты без `ssh` и пересборки стека:
провайдеры моделей, поиск, Telegram, MCP и любые свои переменные. Видят и открывают его
только админы — люди с `admin: true` в `users:`:

```yaml
users:
  - id: trousev
    admin: true      # может править ключи всей инсталляции
  - id: vita         # обычный человек: раздела «Ключи» у неё нет
```

Старый конфиг без объектов продолжает работать: по миграции админом считается один
`trousev`, остальные — обычные люди. Явное `admin: false` забирает флаг и у него.

Как это устроено:

- значения **не показываются** в браузере: панель отдаёт только «задан / не задан» и хвост
  из четырёх знаков, а принимает новое значение;
- панель переписывает `.env`, сохраняя комментарии и чужие строки, и кладёт свои правки в
  **`keys.json`** рядом (в git не попадает, права 600). `keys.json` сильнее `.env`: деплой
  вливает секреты GitHub обратно в `.env`, а настройки панели обязаны это пережить;
- «Убрать» — это `removed` в `keys.json`, а не надежда, что деплой не вернёт строку:
  убранный ключ больше не подхватывается, даже если значение осталось в `.env`;
- после сохранения сервис **перечитывает** `.env`, `keys.json` и `config.yaml`, заново
  пишет людям `auth.json`/`mcp.json` и помечает следующую сессию pi новой. То есть новый
  ключ работает со следующего ответа, а не со следующего деплоя; токен Telegram-бота —
  исключение, ему нужен перезапуск сервиса;
- свежие значения уезжают в процесс pi через `docker exec -e`, поэтому пересоздавать
  контейнеры после смены ключа не нужно;
- над списком ключей — сводка маршрутизации поиска и извлечения, а в каждой строке
  счётчики за семь дней: сколько провайдер отдал и сколько раз отказал. Это **попытки
  роутера**, а не запросы человека: fallback Linkup → Tavily — две попытки. Счётчики
  лежат в `search-usage.json` рядом с `search-router.json`, по дню на запись; восьмой
  день стирается при следующей записи, поэтому файл не растёт.

Люди описываются id и флагом админа: из id выводятся имя контейнера (`icarus-user-probe`),
каталоги `dataDir/users/probe` и id сессии pi. В Telegram тот же id приезжает из
`telegram.mapping`, а HTTP-клиент присылает его заголовком `x-icarus-user-id`. Модели
и ключи общие; MCP — общие из `config.yaml` плюс личные и расшаренные из панели, так что
новый человек — это одна строка.

В `env:` уезжают переменные для расширений: `ICARUS_EXTRACT_AFTER_MS` и `ICARUS_EXTRACT_MODEL` —
разбор разговора в память, `ICARUS_SWEEP_AFTER_HOURS` — интервал уборки памяти (по умолчанию
сутки после разговора, `0` выключает уборку совсем). Уборка приводит полки в порядок: сводит
файлы-близнецы про одно и то же в один, дробит разросшиеся файлы по темам, уводит закрытое из
`identity.md` в проекты. Журналы она не трогает и в промпт не кладёт — только их наличие:
журнал это лента событий, а не полка памяти.

### MCP по требованию

MCP-серверы по умолчанию ленивые: `lifecycle: lazy` — сервер не подключается на старте, и его
инструменты не едут в промпт каждого разговора. В `AGENTS.md` для каждого такого сервера
генерируется подсказка с `mcp_connect`, а `description` объясняет модели, когда сервер нужен.
`lifecycle: eager` — осознанный выбор для серверов, которые нужны всегда; их инструменты
висят в промпте постоянно. `hidden: true` — служебный сервер: он есть у всех и всегда включён,
а в панели его нет, потому что выключать его человеку нечего.

Мост подключается пакетом `pi-mcp-extension@1.8.0`: именно с этой версии появились агентские
`mcp_connect`/`mcp_status`, без них lazy-сервер из разговора не поднять. В 1.5.0 был только
ручной `/mcp:start`, а инструменты ленивого сервера оставались невидимыми.

```yaml
mcp:
  homeassistant:
    url: http://10.0.0.16/api/mcp
    headers: { Authorization: Bearer ${HOMEASSISTANT_TOKEN} }
    lifecycle: lazy                              # дефолт; можно не писать
    description: "Умный дом: свет, климат, сцены" # подсказка модели, в mcp.json не едет
```

Так же живут встроенные умения. Артефакты — сервер `artifacts` с `hidden: true` и `lifecycle: lazy`:
полные инструкции лежат в `instructions` MCP-хендшейка и появляются у модели только после
`mcp_connect`, а в промпте всегда есть лишь короткое описание-триггер. Заговорил человек об
артефактах — инструкции «развернулись»; молчит — контекст не занят.

### MCP из панели: свой сервер за пару минут

То, что лежит в `config.yaml`, — **общие** серверы стека: echo, Maple, Home Assistant. Maple при
этом служебный (`hidden: true`): в панели его нет, выключить себе его нельзя, а журналы расчётов
он держит в рабочей папке разговора, а не в отдельном каталоге. Всё, что человек добавил сам,
живёт не в конфиге, а в `dataDir/mcp/`:

- `registry.json` — описания серверов, кто владелец и с кем поделились;
- `credentials.json` — ключи и OAuth-токены, права `0600`: это такие же секреты, как `auth.json`.

Раздел **MCP** в панели умеет всё, что нужно от «принёс клёвый MCP для TODO»:

- **добавить** сервер: адрес (streamable HTTP или старый SSE) либо команду stdio, которая
  живёт в контейнере человека;
- **включить / выключить** — это личный переключатель на каждого человека. Выключенный сервер
  не попадает ни в `mcp.json`, ни в `AGENTS.md`: он есть в панели, но в разговоре его нет и
  контекст он не занимает. Включённый остаётся `lifecycle: lazy`, поэтому его инструменты
  не висят в каждом промпте, пока сервер не понадобится;
- **поделиться** или оставить только себе. Расшаренный сервер приезжает остальным
  **выключенным** — включают сами. Ключи и OAuth-доступ при этом не копируются: каждый
  настраивает свой, иначе «поделиться сервером» означало бы «поделиться своим аккаунтом»;
- **проверить** — панель сама делает `initialize` и `tools/list` и показывает, сколько
  инструментов отдал сервер (для stdio честно говорит, что проверка будет при подключении).

Авторизация поддерживается вся, что встречается у современных MCP:

| Способ | Что делает панель |
|---|---|
| без авторизации | просто подключает |
| ключ / заголовки | хранит личные `Authorization`/`X-API-Key` и любые другие заголовки; для stdio — переменные окружения |
| OAuth 2.1 | discovery по RFC 9728 / RFC 8414, PKCE S256, `resource` (RFC 8707), refresh token; вход — кнопкой «Подключить» в браузере |
| готовый client_id | использует его, секрет — у каждого свой |
| Dynamic Client Registration | регистрирует клиента сам (RFC 7591), если сервер это умеет |
| Client ID Metadata Document | если сервер поддерживает CIMD и у панели есть публичный HTTPS-адрес |
| ручные endpoints | для упрямых серверов: authorization, token, registration, issuer задаются в форме |

OAuth-поток ведёт сервис, а не pi: pi в контейнере без браузера, и его интерактивная
авторизация рассчитана на TUI. Сервис проходит discovery и обменивает код на токен, но
**в `mcp.json` токен не кладёт**. Туда уезжает ссылка на локальный прокси сервиса
(`http://icarus:<port>/mcp-proxy/<ключ>`): на каждом запросе pi сервис проверяет срок
токена, при необходимости молча обновляет его по `refresh_token` и только потом идёт в MCP.
Поэтому пятиминутный access token (такой выдаёт, например, Black Forest) не протухает
посреди живого треда, а `401` от сервера лечится повтором с уже свежим токеном.

Прокси — это тот же сервис, поэтому он доступен контейнерам людей по имени `icarus` в
compose-сети. Если сервис живёт под другим именем или вне compose, база перекрывается
переменной `ICARUS_MCP_PROXY_BASE` (например, `http://10.0.0.2:8081`). Кнопка
«Переподключить» нужна только если умер сам `refresh_token`.

Если это случилось, человек не остаётся с `invalid_token` в трассировке: прокси
добавляет в ошибку `reauth_url`, веб-чат показывает карточку «Переподключить», а
Telegram — строку со ссылкой на `/panel/mcp?server=<id>`. Панель подсвечивает
нужный сервер и прокручивает к нему.

Для OAuth нужен публичный адрес панели (`url:` в конфиге): callback идёт на
`<url>/panel/mcp/oauth/callback`, а CIMD-документ — на
`<url>/panel/mcp/oauth/client-metadata.json`. Если панель стоит за SSO, который не пускает
этот путь без входа, CIMD-серверы не смогут его скачать; для них остаются DCR и готовый
`client_id`. Серверы, которые умеют только CIMD, требуют исключения для этой страницы в прокси:
на проде оно лежит в `/etc/nginx/custom/chat.trousev.pro.mcp-oauth.conf` — два `location =`
(metadata и callback) без `auth_request`, при этом остальной `/panel/mcp` остаётся за SSO.

Скиллы pi лежат в `~/.pi/agent/skills` человека (каталог монтируется сервисом: `runtime/users/<id>/pi-agent/skills`).
pi показывает модели имена и описания, а тело `SKILL.md` читает по требованию. Пишутся они в панели,
в разделе «Скиллы»; каталог — git-репозиторий, поэтому у скиллов та же история и тот же откат, что у памяти.
Автор скиллов — сама панель: синхронизации с внешним чатом нет, и это осознанно.

## Панель управления

**Icarus Control Panel** живёт на самом icarus (`<url>/` уводит на `/panel`, а он — в `/panel/chat`).
Это прежде всего чат: слева диалоги, справа лента и композер, а за кнопкой в шапке — файлы
рабочей папки текущего разговора. Память, скиллы, MCP и ключи
открываются широкой панелью поверх чата, не уводя со страницы; диалоги при этом
остаются на месте. «Ключи» видит только админ — см. раздел «Ключи в панели» выше.

### Workspace'ы

Workspace — это рабочая папка агента: `/workspaces/<имя>`, у каждой свой `AGENTS.md`, поэтому
поведение в них отличается. Служебное (память, сессии, вложения, персона) лежит рядом, в
`/workspaces/.icarus`, и ни в одну папку не входит — файлы человека остаются его файлами.

- **«Разговор»** (`talk`) — по умолчанию: сюда попадают новые чаты и сюда же возвращаются
  диалоги удалённого workspace'а;
- **«Приватный»** (`private`) — смонтирован только для чтения, и pi не получает ни одного
  инструмента записи (ни `write`/`edit`, ни оболочки), а фоновый разбор памяти в нём не
  загружается вовсе. Память **видна**, но не меняется: человек может говорить о том, о чём
  не хочет оставить запись;
- **свои** — создаются на экране выбора: имя, папка, свой `AGENTS.md`. Удаление убирает
  workspace из списка и возвращает его диалоги в «Разговор», а папку на диске не трогает.
- создание и удаление — это `mkdir`/запись реестра: контейнер не пересоздаётся, живые
  сессии не рвутся. Для API workspace выбирается заголовком `x-icarus-workspace`.

### Чат

- диалоги группируются по дате, ищутся по названию, листаются бесконечным скроллом по 30 штук,
  новый чат — кнопкой в сайдбаре;
- ответ приходит стримом, шаги инструментов собираются в сворачиваемую трассировку (`ПАМЯТЬ`,
  `ПОИСК`, `ДОМ`, `MCP`…), а не вываливаются в текст;
- markdown понимает заголовки, списки, цитаты, код, `~~зачёркнутое~~` и ссылки;
- **вложения**: скрепка, drag&drop или вставка из буфера — до 8 файлов и 10 МБ суммарно.
  Файлы ложатся в `incoming/` человека, картинки модель видит нативно, а в истории остаются
  плашками и миниатюрами;
- **картинки**: модель вставляет `![что на ней](/workspaces/.icarus/incoming/файл.jpg)`, панель рисует.
  Локальные файлы отдаются только из `incoming/` и рабочих папок (`/workspaces/<имя>/…`) — так
  до чата доезжают графики Maple и всё, что агент нарисовал сам; внешние `http(s)`-картинки
  браузер грузит сам. Если человек просит путь — модель пишет путь текстом, без картинки;
- **файлы под рукой**: кнопка в шапке открывает справа дерево рабочей папки текущего
  разговора. Папки раскрываются по клику, файл показывается внизу предпросмотром: markdown —
  как markdown, картинки — картинкой, текст — текстом, остальное честно предлагается скачать.
  Рядом со скачиванием — **«В чат»**: вставляет относительный путь файла в поле ввода (в каретку,
  а если в поле ещё не вставали — в конец) и не переписывает уже набранное. Дерево само
  обновляется после хода агента, а ширина панели, высота предпросмотра и то,
  открыта ли она, запоминаются в браузере. Вглубь панель не выпускает: только один workspace,
  без `..` и символических ссылок наружу;
- **удаление из дерева**: у строки появляется корзина. Файл спрашивает подтверждение, непустая
  папка — тоже (вместе со всем содержимым), а пустая папка удаляется сразу, без вопроса. Сервер
  не удалит непустую папку без явного `force`, корень workspace'а не трогает вовсе, а корневой
  `AGENTS.md` защищён: это инструкции агента, и без них workspace теряет правила;
- канал уезжает в pi переменной `ICARUS_CHANNEL`: в веб-чате персона знает про markdown-картинки,
  в Telegram этого блока нет — там картинки пока не отправляются;
- чат ходит в те же сессии pi, что и Telegram: тот же контейнер, та же память, свой разговор на диалог.
- **субагенты видны живьём**: под шагом `СУБАГЕНТЫ` список детей — кто работает, чем занят, кто
  в очереди, кто упал; в истории этот список остаётся после хода;
- **остановить ответ можно на середине**: пока идёт ход, на месте «отправить» стоит «■» — он шлёт
  abort, и вместе с ходом гаснут работающие субагенты;
- **команды — как в Telegram**: наберите `/` — над полем откроется палитра. В ней свои команды
  (`/compact`, `/stop`, `/stats`, `/clear`, `/rename`, `/skills`, `/help`) и команды pi: скиллы,
  промпт-шаблоны и команды расширений. `/compact` и `/clear` — это RPC pi (`compact` и `new_session`),
  так что контекст сжимает и начинает заново сам pi; `/rename` меняет имя чата в `chats.json`, и оно
  сразу видно в шапке и сайдбаре. `/clear` не выбрасывает ленту: старые сообщения остаются выше
  разделителя «Контекст очищен», и после перезагрузки собираются заново из цепочки сессий.
  `/compact` и `/stats` работают и посреди ответа. Выбор из палитры — стрелки и Enter (или клик),
  имя команды с аргументами дописывается в поле; команда pi уезжает в разговор обычной репликой.
  Ответ остальных команд — служебная плашка в ленте: в файл сессии он не пишется, поэтому после
  перезагрузки ленты его не видно — в отличие от Telegram, где он остаётся отдельным сообщением;
- **видны все разговоры человека**, а не только начатые в панели: `chats.json` — общий реестр
  веб-чата, Telegram и API. В нём только `id`, `title`, `createdAt`, `channel`, `conversationId`
  и `sessions` — цепочка сессий pi (появляется после `/clear`, чтобы старые сообщения остались
  историей, а новая сессия стала текущим контекстом);
  превью и время последнего сообщения панель читает из `sessions/*.jsonl` — и только для той
  страницы списка, которую показала;
- **пагинация**: `GET /panel/api/chats?limit=30&cursor=…` отдаёт страницу и `nextCursor`, а сайдбар
  догружает следующую при скролле. Сортировка — по `createdAt`, поэтому порядок не прыгает от нового
  сообщения; поиск идёт по названию из реестра, без чтения историй;
- Telegram и API — **только для чтения**: композер в них выключен, а сервер отказывает `chat/send`
  и `chat/abort`; продолжать разговор нужно там, где он начат;
- **миграция старого формата** идёт на старте и идемпотентна: `chats.json` нормализуется
  (`preview`/`updatedAt` выбрасываются, `channel` и `conversationId` достраиваются), старый файл
  один раз сохраняется как `chats.json.bak`; `session-index.json` переносится в реестр и удаляется;
  всё, что уже лежит в `sessions/`, дописывается в реестр; давние сессии без `conversationId`
  попадают туда как `session:<id>`. Битой `chats.json` откладывается в `.corrupt-*`, а не затирается.


### Память

Память правится построчно: видно, из какого коммита пришла каждая запись, лишнее снимается галочками
и уезжает одним коммитом, файл можно удалить целиком или скачать. История — по файлу, с диффом и
откатом.

### Скиллы

Скилл — это каталог с `SKILL.md` (`pirate-mode/SKILL.md`) и, если нужно, файлами бандла рядом.
В панели видно список скиллов с их описаниями, а открытый скилл правится целиком: имя, описание,
теле инструкции и галочка «скрыть от модели» (тогда pi зовёт скилл только командой `/skill:имя`).

- **сохранение — это коммит** в репозитории скиллов: историю видно в панели, откат возвращает скилл
  вместе с бандлом, а удаление сначала фиксирует то, что ещё не попало в git, — иначе откат вернул бы
  один `SKILL.md` без файлов, которые человек положил руками;
- **после сохранения скилл доезжает до Икара сам.** Каталог скиллов pi читает один раз при старте
  процесса, поэтому панель помечает ресурсы человека как обновившиеся: идущий ход доигрывает на
  прежнем наборе, а следующий ответ поднимает pi заново (см. `SessionRegistry.bumpResources`);
- **имя и описание проверяются по спецификации** Agent Skills: имя — строчные латинские буквы, цифры
  и дефис, описание обязательно. Без описания pi пропустил бы скилл молча — панель про это скажет
  и не сохранит;
- **«напиши за меня»** — рассказываешь идею одной фразой, модель собирает имя, описание и инструкцию.
  Черновик ложится в редактор, а файл и коммит делает «Сохранить»: что уедет Икару, человек видит
  до сохранения. Модель отвечает разово, без тулов, сессии и скиллов (`--no-tools --no-session
  --no-skills`) и там же, где живут ключи и pi, — то есть в контейнере человека. Имя из ответа
  приводится к правилам, занятое получает номер, а если латиницы в нём не оказалось, панель
  оставит поле пустым с пометкой — инструкция при этом не пропадёт.

Плоские `*.md` в корне каталога pi тоже считает скиллами: панель показывает и правит и их, но новые
заводит каталогом — в каталоге помещаются скрипты и справки, на которые скилл ссылается.

Пароля у панели нет: человека называет **SSO-прокси**, за которым она стоит. На проде это nginx с
Authelia — он подставляет `Remote-User` из ответа `/api/verify` и перетирает всё, что клиент прислал
сам, а `icarus` читает этот заголовок (`panel.userHeader`) и проверяет, что человек есть в `users`.
Отсюда два следствия:

- **порт icarus не должен смотреть наружу мимо прокси.** Кто дотянется до него напрямую, тот
  назовётся любым именем: на проде порт `8081` смотрит только на `127.0.0.1`, а наружу его
  выставляет nginx с Authelia;
- локально, где прокси нет, панель пустит только с `panel.devUser: <id>` в `config.yaml` — сервис
  при этом ругается в лог, потому что на проде так делать нельзя.

Одноразовых ссылок и ключей в панели больше нет: старые ссылки с `?t=…` работают, просто параметр
игнорируется, а вход решает прокси. Икару панель называет инструмент `get_control_panel_link`.

### Артефакты

Артефакты — **глобальная библиотека** `<dataDir>/artifacts/`, одна на всю семью. Она монтируется
в контейнер каждого человека как `/artifacts`, поэтому список общий, а не «мои файлы в workspace».
Артефакт — папка `/artifacts/<slug>/` с одним index-файлом:

| Файл | Тип |
|---|---|
| `index.html` | HTML-страница |
| `index.md` | Markdown-документ |
| `index.csv` / `index.tsv` | Таблица: поиск и сортировка в панели |
| `index.png` / `index.jpg` / `index.svg` | изображение |

Таблица — это обычный CSV/TSV, первая строка — заголовки колонок. Панель сама рисует из него
таблицу с поиском и сортировкой по клику на заголовок; колонки, где все значения числовые,
сортируются как числа. Свой HTML для таблицы не нужен, а «без панели» отдаёт такую же
интерактивную страницу, а не голый текст. Скачивание (`?download=1`) отдаёт исходный CSV/TSV.

И всегда `index.ai.md` — короткое описание для ИИ: заголовок H1, о чём артефакт, что внутри,
что можно менять. Остальные файлы (стили, картинки, шрифты) лежат рядом; ссылки внутри HTML —
относительные. Наружу `index.ai.md`, `.artifact.json` и `.folder-acl.json` не отдаются: панель
читает их через API, где уже проверены права.

```text
/artifacts/plan-na-chetverg/
  index.md            # то, что видит человек
  index.ai.md         # то, что читает ИИ
  images/standup.png
  .folder-acl.json    # владелец и права
  .artifact.json      # publicId, если ссылку уже просили
```

**Создаёт артефакты сам pi**, но с одной оговоркой: папку и права заводит `artifact_new`, а файлы
пишутся обычными `write`. Без этого писать в `/artifacts` нельзя — generic folder-guard проверяет
`.folder-acl.json` у каждой папки и блокирует `read`/`write`/`edit`/`grep`/`find`/`ls`, куда
человеку нельзя, а `bash` с абсолютным путём к `/artifacts` запрещён целиком, чтобы права не обходились.
MCP `artifacts` (`tools/artifacts-mcp/`) читает `index.ai.md` вместо HTML и выдаёт ссылку;
инструменты: `artifact_list`, `artifact_read`, `artifact_new`, `artifact_link`, `artifact_check`.

**Права — матрица «субъект × уровень».** У папки есть владелец и два субъекта:

- **я** (`me`) — владелец артефакта;
- **семья** (`family`) — все остальные.

Уровни: **none ⊂ read ⊂ write ⊂ admin**. `none` — артефакта нет в списках панели и MCP, его
нельзя прочитать или изменить; это уровень для очень личных вещей (имя папки при этом может быть
видно в общем листинге `/artifacts`, но содержимое недоступно). `write` умеет и читать, `admin` —
ещё менять права, удалять артефакт и делать публичную ссылку. По умолчанию `me=admin`,
`family=none`: новый артефакт личный, пока владелец не откроет его семье в диалоге «Поделиться».
Владелец управляет своим артефактом всегда, даже если выставил себе `read` — иначе можно было бы
заблокировать себя навсегда; выставить себе `none` ему нельзя, иначе артефакт пропадёт из его
списка. Права меняются в панели кнопкой «Поделиться»: в одном диалоге — мой уровень, уровень
семьи и публичная ссылка; панель, MCP и folder-guard читают один и тот же `.folder-acl.json`.

**История версий — прозрачная, но обязательная.** Каждый артефакт — маленький git-репозиторий
внутри своей папки. Человек про git не знает: в панели «История» открывается боковой панелью,
клик по версии показывает её в предпросмотре, а «Вернуть эту версию» меняет артефакт только после
подтверждения. Снимки делает императивный слой, а не ИИ:

- перед `write`/`edit` в артефакт расширение pi фиксирует состояние «как было» (если истории ещё нет);
- после успешного `write`/`edit` — коммит с понятным именем (`write index.md`, `edit style.css`);
- в конце каждого хода `turn_end` добирает всё, что пришло через MCP или другие инструменты;
- при старте сервис заводит историю у всех существующих артефактов.

Служебные `.folder-acl.json` и `.artifact.json` не версионируются: откат контента не должен менять
права и публичную ссылку. Сам `.git` скрыт от панели, публичных маршрутов и файловых инструментов
агента (folder-guard блокирует `.git` и служебные файлы). «Вернуть» не переписывает историю: делает
новый коммит, который возвращает дерево к выбранной версии, поэтому старые версии остаются доступны.

**Чат правки артефакта.** Рядом с «Историей» — кнопка-иконка чата: она открывает боковую панель с
разговором про этот артефакт. Это не отдельный агент и не второй вид чата — тот же веб-разговор с
тем же файлом сессии, но помеченный артефактом. По этой пометке реестр запускает pi **в папке
`/artifacts/<slug>`**, а не в workspace, а персона собирает промпт про конкретный артефакт: где его
главный файл, что `index.ai.md` — описание для ИИ, что историю и права ведёт система, а чужие папки
трогать нельзя. В общем списке чатов такой разговор виден как «Правка · <название>» и продолжается
с того же места. Кнопка доступна только при праве `write`: остальным она обещала бы правку, которую
сервер всё равно отклонит. Один артефакт — один разговор; повторное открытие возвращает его же.
Команды в боковой панели те же, что в большом чате: строка с косой черты сначала уходит в
`/panel/api/chat/command`, и только отказ сервера отправляет её в pi обычной репликой. Поэтому
`/clear` здесь действительно начинает новый контекст: старые ходы остаются выше разделителя
«Контекст очищен», а разговор остаётся при своём артефакте — `/clear` отвязывает контекст, не папку.

**Панель.** «Артефакты» — отдельная дверь в сайдбаре чата, на одном уровне с «Настройками».
Список глобальный: все доступные артефакты с типом, размером и владельцем. Справа просмотр:
HTML в песочнице, картинка на тёмном фоне, markdown тёмной типографикой. Там же поиск и ряд
иконок: «Поделиться» (права и ссылка), «История», чат правки, полный экран без панели,
скачивание и удаление в `artifacts/.trash/` (не навсегда). Переключателя workspace больше нет:
артефакт не принадлежит workspace.

**Публичная ссылка** — `/a/<артефакт>/<publicId>/`. `publicId` — случайные 18 байт в скрытом
`.artifact.json`, а не имя папки: угадать чужой артефакт нельзя, а отозвать ссылку можно,
переключив публичный доступ на «нет доступа» в диалоге «Поделиться» (тогда удаляется `publicId`). Внутренняя ссылка, которую Икар даёт по умолчанию, —
`/panel/artifacts?artifact=…`; публичная создаётся только по прямой просьбе и требует `admin`.
По умолчанию публичная ссылка открывает артефакт **внутри панели**; `?bare=1` отдаёт тот же
артефакт без панели, а прямой путь на `index.html`/`index.png` — сам файл. HTML и SVG уезжают
с `Content-Security-Policy: sandbox`, поэтому код артефакта не дотянется до SSO-куки и API панели.
Старые ссылки `/a/<человек>/<workspace>/<артефакт>/<id>/` редиректят на новый адрес.

Чтобы ссылка была **действительно публичной**, SSO-прокси должен пропускать `/a/` без
`auth_request`: сервис сам входа не требует, но nginx с Authelia по умолчанию закрывает весь
домен. На проде это отдельный `location /a/` с отключённым `auth_request` — как у OAuth-callback
MCP. Если этого не сделать, ссылка откроется только у вошедших.

Старые артефакты из `workspace/artifacts/` сервис при первом запуске переносит в общую библиотеку:
владельцем становится автор workspace, ACL — `me=admin, family=none`, publicId сохраняется.
Старый публичный адрес продолжает работать через редирект.

Включается строкой в `mcp:` — она уже есть в `config.example.yaml`; в существующем `config.yaml`
её нужно добавить (или обновить конфиг из примера). Код сервера сервис монтирует в контейнер
сам, отдельной установки не нужно.

**Инструкции спрятаны до первого упоминания.** MCP помечен `hidden: true` (в панели MCP его нет,
выключить нельзя) и `lifecycle: lazy`: его инструменты и полные правила не висят в каждом разговоре.
В `AGENTS.md` едет только короткий триггер — описание сервера. Заговорил человек об артефактах,
модель зовёт `mcp_connect`, получает `instructions` в MCP-хендшейке и работает по ним. Так «спрятать
инструкции» не значит «модель о них не узнает»: она узнаёт ровно тогда, когда это нужно.

### Посмотреть локально

`./script/panel` поднимает панель без сборки стека: тот же код, тот же `dataDir`, те же файлы и git.
Чат в ней работает, если контейнеры людей уже подняты, — панель говорит с теми же сессиями pi, что
и сервис, но сама контейнеры не создаёт.

```bash
./script/panel                    # http://127.0.0.1:8099/panel, первый человек из users
./script/panel --user probe2      # посмотреть другого человека
./script/panel --with-model       # ещё и «напиши за меня» в редакторе скиллов
./script/panel --port 8099 --config /path/config.yaml
```

Человека в локальной панели называет `panel.devUser` (SSO-прокси рядом нет), а слушает она только
петлю: панель без входа наружу не выставляется. Нет поднятого стека — чат честно ответит, что сессия
недоступна, а память и скиллы продолжат работать. Кнопка «напиши за меня» появляется с `--with-model`:
тогда разовый вопрос уходит в контейнер человека, как в сервисе, а без флага блока в редакторе нет
вовсе, чтобы не обещать несуществующее.

## Субагенты

Модель может раздать работу отдельным процессам pi — инструмент `subagent`. Зачем: контекст. Шесть
поисковых запросов по две-три страницы выдачи в одном разговоре утопят окно; ребёнок читает страницы
сам и возвращает только вывод. Родитель платит за результат, а не за дорогу к нему.

- **Вызов блокирующий.** Инструмент не возвращается, пока не закончилась последняя задача: пока
  субагенты работают, хода нет и ответ человеку не уезжает. Никаких «запустил и побежал» — у pi нет
  фоновых инструментов, и это здесь скорее хорошо.
- **Очередь, а не стая.** За вызов принимается до 40 задач, но одновременно работают
  `ICARUS_SUBAGENT_CONCURRENCY` (по умолчанию 4, потолок 8), остальные ждут в порядке объявления.
  Четыре — не от жадности: у Anthropic в исследовательском агенте ведущий запускает 3–5 субагентов
  параллельно, а «50 субагентов на простой вопрос» они называют своей ранней ошибкой; OpenClaw держит
  рядом те же числа — 4 на основную линию и 8 на детей. Потолок 8 считается на весь процесс: даже
  если модель позовёт инструмент дважды в одном сообщении, детей всё равно не больше восьми.
- **Вложенности нет.** Ребёнок запускается с `ICARUS_SUBAGENT_DEPTH=1`, инструмент ему не
  регистрируется, а `--exclude-tools subagent` и `--no-extensions` страхуют. Субагент субагента не
  запустит: это не «больше работы», а счёт за токены.
- **Роли.** `scout` — быстрый, читает файлы и смотрит каталоги; `researcher` — веб-поиск, чтение
  страниц и файлов (`read`, `find`, `ls`); `worker` — всё, что есть у Икара: восемь встроенных
  инструментов pi (включая `grep`/`find`/`ls`, которые у pi не входят в набор по умолчанию),
  веб-поиск, время и ссылка на панель. MCP-инструменты работнику нарочно не выдаются: их имена
  приходят от серверов динамически, а субагент с доступом к дому — это чужие кнопки, не «ещё руки».
  Модель для ребёнка берётся по уровню:
  `ICARUS_MODEL_FAST` / `ICARUS_MODEL_STRONG` сервис кладёт в контейнер сам из `models`, так что
  уровни не приходится дублировать в `env`.
- **Видно всё.** В веб-чате под шагом `СУБАГЕНТЫ` живой список детей: кто работает, чем занят, кто в
  очереди, кто упал и почему; после хода он остаётся в истории. В Telegram строка статуса показывает
  «⚙ агенты 2/5 · researcher: web_search: amazon.ie».
- **Остановить можно на середине.** В панели — кнопка «■» на месте «отправить», в Telegram — `/stop`.
  Abort доезжает до инструмента, тот гасит процессы детей (SIGTERM, через 3 с SIGKILL) и очередь.
- **Новая реплика прерывает ход.** В Telegram человеку никто не мешает написать поверх: бот чистит
  очередь сообщений pi, шлёт abort, ждёт `agent_settled` и начинает новый ход. Если новый ход сам
  решит позвать субагентов — позовёт.
- **Персона и память детей не касаются.** Ребёнок получает свой системный промпт и только те
  расширения, которые нужны роли (исследователю — веб-поиск). Персона, разбор и уборка памяти в нём
  не грузятся: иначе каждый ребёнок оставлял бы след в памяти разговора. Скиллы при этом работают —
  ими и удобно раздавать задачи вроде «пройди по этому скиллу».

Пределы живут в `env:` контейнера в `config.yaml`:

```yaml
env:
  ICARUS_SUBAGENT_CONCURRENCY: '4'        # одновременно работающих детей (1–8)
  ICARUS_SUBAGENT_MAX_TASKS: '40'         # задач за один вызов (потолок очереди)
  ICARUS_SUBAGENT_TASK_TIMEOUT_MS: '300000'  # одна задача: дольше — таймаут
  ICARUS_SUBAGENT_BUDGET_MS: '900000'     # весь вызов: дольше — остаток очереди пропускается
```

Команда запуска ребёнка по умолчанию — `pi` из `PATH`; `ICARUS_SUBAGENT_PI` перекрывает её, если в
образе бинарь называется иначе. Код расширения — `packages/extensions/subagent.ts`; сервис копирует
его в `~/.pi/agent/extensions` вместе с остальными, отдельной настройки не нужно.

## Сессии и сжатие

Сессия pi — это один разговор в контейнере человека. Пока человек пишет, она живёт; после
`sessionIdleMinutes` (по умолчанию час) тишины icarus считает разговор законченным и делает по порядку
две вещи:

1. **сжимает** контекст — `compact` в pi: модель пересказывает старую часть разговора, и в файл сессии
   дописывается пересказ. Дальше в промпт едет он и недавние реплики, а не вся история: разговор
   продолжается дешевле и не упирается в окно;
2. **гасит процесс** pi. Контейнер человека остаётся поднятым, история — в `/workspaces/.icarus/sessions`.

Следующая реплика поднимает сессию заново по тому же файлу — уже со сжатой историей. Пока человек
говорит, сжатия нет: занятые сессии уборка пропускает, а переполнившееся посреди разговора окно pi
сжимает сам. Сбой сжатия сессию не оставляет висеть: закрываем как есть — история цела, файл сессии
append-only. Правило одно на все входы — Telegram и OpenAI-клиент.

## Telegram

Бот — основной вход к тому же Икару: та же память, тот же контейнер, свой разговор на чат. Людей он сам
не заводит: человека узнаёт по username из сообщения и берёт id из `telegram.mapping` в `config.yaml`
(тот самый id, что в `users`; от него зависят каталоги памяти и имя контейнера). Незнакомцу бот отвечает
подсказкой, а не разговором: без карты непонятно, чья это память и чей контейнер.

```yaml
telegram:
  mapping:
    '@trousev': trousev        # telegram username → id человека из users
```

Токен в конфиге писать не нужно: он берётся из `.env` (`TELEGRAM_BOT_TOKEN`, образец `.env.example`).
Нет токена или пусто в `mapping` — бот не поднимается, а сервис работает как раньше. Маппинг
принимается и отдельным ключом `telegram_mapping` — ровно как он читается глазами. Username в yaml
обязан быть в кавычках: с `@` начинаются зарезервированные конструкции, и `@trousev: trousev` не
разберётся («Plain value cannot start with reserved character @»).

Устройство простое: длинный опрос `getUpdates` — вебхук не нужен, ни домена, ни сертификата. Разговор
свой на чат и топик (`telegram-<chat id>`, в группе — с id человека: иначе двое в одной группе дрались
бы за одну сессию pi; с топиками — ещё и с его номером). Ответ доезжает правками одного сообщения:
сначала «…», потом текст по мере хода, а строка «⚙ читаю …» показывает, чем Икар занят, и в готовый
ответ не попадает. Ответ длиннее 4096 знаков разрезается на несколько сообщений. Сообщения одного
чата (и топика) обрабатываются по очереди, разные чаты друг друга не ждут.

Очередь — не приговор: если человек пишет поверх идущего хода, бот прерывает его. Чистится очередь
сообщений pi, уходит abort, бот ждёт `agent_settled` и только потом отправляет новую реплику —
поэтому субагенты, которые держали ход, гаснут, а ответ приходит уже на новое сообщение. Пока ход
встаёт, человек видит «…», а не молчание.

### Топики в Telegram

Если в боте включён Threaded Mode, человек заводит топики сам — кнопкой «All Messages» в шапке
чата; отдельной команды у бота больше нет. Один топик — один разговор: своя история, свой процесс
pi и свой `/compact`. Бот узнаёт о новом топике по служебному сообщению `forum_topic_created` и
просто относит к нему сообщения — заводить топики за человека ему больше не нужно.

`/rename Имя` переименовывает текущий разговор. Если он идёт в топике, меняется и имя топика в
Telegram; в любом случае новое имя ложится в `chats.json`, и панель показывает его в списке
разговоров. Имя, выбранное человеком в клиенте Telegram, бот не трогает.

С общей лентой («All Messages») есть тонкость, из-за которой разговоры и терялись: когда человек
начинает печатать **в ленте**, клиент Telegram заводит топик сам, а само сообщение приезжает боту как
сообщение корня — без `message_thread_id`. Раньше бот считал такое сообщение корневым: ответ уезжал в
ленту, а свежий топик оставался пустым, и разговор разъезжался на два. Теперь бот помнит свежий топик
(`FRESH_TOPIC_WINDOW_MS`, минута) и относит к нему первое сообщение из ленты: ответ, «печатает…» и
`conversationId` — как у топика.

Отправку в топик Telegram иногда отбивает («message thread not found»; в мае 2026 так ломались топики
в личке у всех) или, что хуже, молча кладёт сообщение в общую ленту, отвечая `ok: true`. Поэтому бот
сверяет ответ (`message_thread_id`/`is_topic_message`), при отказе повторяет ответом на реплику
человека — якорь уводит ответ в тот же топик, — а если и это не вышло, честно пишет в корень чата,
что ответа в топике не будет. Молча ответ не теряется.

**Разметка.** Модель отвечает markdown, а Telegram без `parse_mode` показывает его как есть —
звёздочками, решётками и обратными кавычками. Живой режим тут один: `MarkdownV2` требует
экранировать полтора десятка знаков, и одна «2+2=4» в ответе роняет отправку целиком
(«can't parse entities»). Поэтому ответ уезжает HTML, а разметку под него собирает
`packages/service/src/telegram/format.ts`: жирный, курсив, зачёркнутый, спойлер, инлайн-код,
блоки кода с подсветкой, цитаты и ссылки. Чего у Telegram нет — заголовков, списков и таблиц —
рисуем тем, что есть: жирной строкой, буллетами и моноширинным блоком с выровненными колонками.
Ответ приходит кусками, поэтому недописанная разметка не ошибка: незакрытая пара остаётся
текстом, незакрытый блок кода закрывается в конце. А если Telegram всё-таки отверг разметку,
бот повторяет то же сообщение без тегов: ответ важнее курсива.

Что под капотом: один разговор (корень чата или топик) — один `conversationId`
(`telegram-<chat id>-<thread id>`), а значит своя сессия pi со своим процессом внутри **общего**
контейнера человека и свой файл истории в `<dataDir>/users/<человек>/sessions`. Час тишины
(`sessionIdleMinutes`) — сессия сжимается моделью и процесс гасится; следующая реплика поднимает pi
заново по тому же файлу, и разговор продолжается с пересказа. Тот же механизм переживает перезапуск
сервиса и пересоздание контейнера: история лежит на хосте, а не в памяти процесса. Сообщения одного
разговора идут строго по очереди, разные разговоры друг друга не ждут.

**Фото.** Картинка идёт тем же путём, что и вложение из OpenAI-совместимого чата: бот забирает файл из Telegram (у
Bot API это два запроса — `getFile` за путём и сам файл), кладёт его в `incoming/` человека и отдаёт
модели нативно, а путь к файлу едет в реплике — по нему картинку найдёт и тул. Подпись к фото
становится текстом реплики; фото без подписи Икар видит просто картинкой. Картинка документом (так
присылают скриншоты без сжатия Telegram) сохраняется под своим именем.

**Голосовые.** Модель звука не слышит, поэтому голосовое сначала расшифровывается отдельным запросом
к провайдеру — метод `/audio/transcriptions`, у DeepInfra это Whisper, — тем же ключом, что и модели.
Реплика уезжает с пометкой «[голосовое, 12 с]»: Икар должен знать, что это диктовка, а не текст с
пунктуацией. Пока расшифровка идёт, в сообщении видно «🎤 слушаю голосовое». Ключа провайдера нет —
бот честно говорит, что голосовых не разбирает; выключить совсем — `speech: none`.

```yaml
speech:                        # чем расшифровывать голосовые; по умолчанию Whisper у DeepInfra
  language: ru                 # подсказка распознавателю, необязательна
```

Видео, стикеры, аудиофайлы и документы, которые не картинки, бот не разбирает и говорит об этом
словами. Слишком большое вложение (Bot API отдаёт не больше 20 МБ) тоже честно называет причиной.

Команд у бота семь, и каждая решает своё, не отправляя команду репликой в разговор:

- `/compact [пожелание]` — подвести итог сейчас: pi сжимает контекст своим RPC `compact`. Пожелание
  уезжает pi как инструкция к пересказу: «сохрани про математику». Работает и в затихшем разговоре —
  сессию поднимем;
- `/stop` — прервать ход, вместе с работающими субагентами. Идёт мимо очереди сообщений: ход,
  который он отменяет, сейчас в работе, и ждать его конца значило бы не отменить ничего;
- `/stats` — сколько реплик, токенов и денег ушло и сколько занято в контексте;
- `/clear` — начать разговор с чистого листа: pi по RPC `new_session` заводит новую сессию, а
  сервис дописывает её в цепочку `sessions`. Старые сообщения остаются в ленте до разделителя
  «Контекст очищен», новый контекст начинается после него; память не трогается — человеку так
  и говорим, иначе он решит, что стёр память;
- `/rename <имя>` — переименовать текущий чат: имя ложится в `chats.json` и видно в панели; если
  разговор идёт в топике Telegram, переименовывается и топик;
- `/skills` — что можно позвать в чате: скиллы человека, промпт-шаблоны и команды расширений
  (их список отдаёт сам pi, см. `get_commands`);
- `/help` — то же меню, что Telegram показывает по кнопке.

`/start`, который Telegram шлёт сам при первом заходе, отвечает приветствием. Строка с косой черты,
которой бот не знает, получает подсказку — но только если это одно слово: `/fix-tests прогони` и
`/skill:brave-search` уезжают в pi как обычная реплика, потому что у pi есть свои команды, и отбирать
их у человека незачем.

В веб-чате те же семь команд: разбор и тексты общие, лежат в `sessions/commands.ts`, а запускает их
`POST /panel/api/chat/command`. `/compact` и `/clear` и там идут в pi теми же RPC, а `/rename`
меняет имя в `chats.json`. Команды pi палитра берёт из того же `get_commands`, что и `/skills`.

## Проверки

На каждый PR и на push в `main` крутится [`.github/workflows/ci.yml`](.github/workflows/ci.yml):
`./script/lint` и `./script/test` на node 22 и 24. Локально ровно то же самое:

```bash
./script/lint && ./script/test
```

`eslint` идёт с базовым набором правил самого ESLint (`js.configs.recommended`) и с node-глобалями
для `.js`/`.mjs` — иначе правила typescript-eslint не ловят ни `no-duplicate-case`, ни
`no-fallthrough`, ни `no-useless-assignment`. `shellcheck` нужен только шагу `shell`: машина без
него получит предупреждение и пропуск, а CI упадёт, потому что в ubuntu-образе GitHub он есть
из коробки.

`main` защищена настройками ветки, а не уговорами:

- прямой push запрещён, включая админский (`enforce_admins`) — только PR;
- merge PR заблокирован, пока не позеленели все четыре проверки CI (job'ы `lint` и `test`
  на node 22 и 24);
- свежесть ветки PR относительно `main` не требуется: проверки гоняются на самом PR, а
  догонять `main` — забота автора (`strict` в required status checks выключен осознанно);
- force-push и удаление `main` запрещены.

Имена job'ов и матрица — часть этой защиты. Меняешь `name` в `ci.yml` — обнови required status
checks в настройках ветки, иначе PR навсегда повиснет на «Expected — Waiting for status to be
reported».

Сборки нет: код исполняется напрямую как TypeScript (`node src/index.ts`), поэтому `tsc` работает
только проверяльщиком и ничего не пишет на диск. TypeScript пока 6.x — typescript-eslint ещё не
умеет 7-ю ветку, так что при обновлении зависимостей это ограничение стоит держать в голове.

## Деплой

Прод — `trousev.pro`: чекаут в `~/deployments/icarus` и стек `docker compose`, который
поднимает `./script/server -d`.

Push в `main` запускает [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml):
GitHub по SSH заходит на `trousev.pro` под `trousev`, обновляет чекаут (`git fetch` +
`git reset --hard origin/main`) и зовёт [`./script/redeploy`](script/redeploy). Тот
ставит node, если на хосте он старее 22.19 (официальная сборка в `~/.local/share/icarus`),
гоняет `./script/update`, переносит секреты в `.env`, правит `config.yaml` через
`render-config.ts` (люди, порт, `dataDir`, `apiKey`, маппинг Telegram, час тишины), поднимает стек и падает, если
`/healthz` не подтвердил, что сервис и контейнеры людей на месте. Руками то же самое:
`ssh trousev@trousev.pro`, `cd ~/deployments/icarus`, `./script/redeploy` (`--no-cache`
собирает образы с нуля).

`config.yaml` и `.env` на хосте деплой переживают — они в git не попадают. А вот
правки трекаемых файлов `git reset --hard` стирает: код на проде меняется только через PR.

Ключи, заданные в панели (раздел «Ключи», только админ), лежат в `keys.json` рядом с
`.env` и **сильнее него**: деплой вливает секреты GitHub обратно в `.env`, но значения
из панели остаются в силе. Это значит, что поменянный в панели `DEEPINFRA_API_KEY`
не перезапишется секретом из GitHub; чтобы вернуть секрет GitHub, ключ в панели надо
убрать. Флаг админа `render-config.ts` сохраняет у тех, кто остался в `ICARUS_USERS`,
а новым людям выдаёт его по миграции только `trousev`.

Настройки прода живут в GitHub:

| имя | где | что |
| --- | --- | --- |
| `ICARUS_USERS` | переменная environment `production` | люди через пробел или запятую — из неё собирается `users:` в `config.yaml` |
| `ICARUS_DNS` | необязательная переменная environment `production` | DNS-серверы контейнеров (`docker.dns`); не задана — дефолт из `script/redeploy`, `none` — убрать |
| `ICARUS_URL` | необязательная переменная environment `production` | внешний адрес панели управления (`url`): его Икар называет человеку в чате; не задана — `script/redeploy` ставит `https://chat.trousev.pro/`, локально по умолчанию `http://localhost:8081` |
| `ICARUS_SESSION_IDLE_MINUTES` | необязательная переменная environment `production` | сколько минут тишины означают «разговор закончен», после чего icarus сжимает сессию pi и гасит её; не задана — `script/redeploy` ставит 60 (час) |
| `ICARUS_MCP_PROXY_BASE` | необязательная переменная environment `production` | база локального прокси OAuth-MCP, которая уезжает в `mcp.json`; не задана — `http://icarus:<port>/mcp-proxy` (имя контейнера сервиса в compose) |
| `ICARUS_TELEGRAM_MAPPING` | необязательная переменная environment `production` | кто из Telegram чей человек: `@trousev:trousev,@vita:vita` (значения — id из `ICARUS_USERS`). Из неё собирается `telegram.mapping` в `config.yaml`; `none` — убрать маппинг, пусто — не трогать |
| `ICARUS_API_KEY` | секрет environment `production` | Bearer для OpenAI-совместимого эндпоинта (`apiKey` в `config.yaml`) |
| `DEEPINFRA_API_KEY` | секрет environment `production` | ключ провайдера — уезжает в `.env` |
| `TAVILY_API_KEY` | секрет environment `production` | ключ веб-поиска — тоже уезжает в `.env` |
| `TELEGRAM_BOT_TOKEN` | секрет environment `production` | токен бота от @BotFather — уезжает в `.env`, оттуда его читает `config.yaml` |
| `DEPLOY_HOST` | секрет environment `production` | `trousev.pro` |
| `DEPLOY_SSH_SECRET` | секрет environment `production` | приватный ключ `github-actions-deploy@icarus`; его публичная часть — в `~/.ssh/authorized_keys` на хосте |

Секреты лежат именно в environment `production`, а у него правило «разрешена только
ветка `main`»: репозиторий публичный, и секреты уровня репозитория читала бы любая ветка.

`ICARUS_USERS` — это **id человека**, а не имя и не username. По нему выводятся имя
контейнера, каталог памяти и id сессии pi; в Telegram человек сопоставляется с этим id
через `ICARUS_TELEGRAM_MAPPING`, а HTTP-клиент присылает его заголовком
`x-icarus-user-id`. На проде это логины, под которыми люди ходили в чат раньше:
каталоги в `runtime/users/<id>` названы по id, поэтому смена id — это ещё и перенос
каталога. Проверить, кого видит icarus, можно по `/healthz`: он отдаёт `users`
и состояние контейнеров (`missing` должен быть 0).

После переезда панели на `chat.trousev.pro` `script/redeploy` ставит этот адрес сам.
Если в `ICARUS_URL` (variables environment `production`) уже лежит старый
`memory.trousev.pro`, поменяй или убери её: явно заданная переменная сильнее дефолта.

Переносить каталог мало: **после переноса контейнеры надо пересоздать**
(`docker compose -f docker-compose.yml up -d --force-recreate`) — `up -d` тут не поможет,
compose не видит изменений. Bind mount резолвится один раз при создании контейнера, и
переименованный каталог контейнер продолжает видеть старым (пустым) — теряются `auth.json`
и `models.json`, которые icarus пишет при старте, и pi отвечает «Model … not found»,
а стрим рвётся «RPC-канал закрыт». При этом на хосте всё на месте, и `./script/server -d`
сам по себе тоже молчит: `Container … Running`. Проверка одной командой:
`docker exec icarus-user-<id> ls /home/node/.pi/agent/` — там должны быть `auth.json`,
`models.json`, `skills/`.

Прод-специфику деплой подставляет сам: `dataDir` внутри чекаута (`runtime/`, в git не попадает).
Порт `8081` — общий дефолт (`config.example.yaml` локально и `script/redeploy` на проде): он выбран
потому, что на прод-хосте `8080` занят jitsi-jvb, а локально удобнее тот же порт, что в бою.

Отдельная грабля хоста — резолвер. Docker отдаёт контейнерам серверы из `/etc/resolv.conf`
хозяина, и если локальный резолвер не пускает docker-подсети, каждый внешний запрос
сначала ждёт таймаут. Так, `unbound` с `access-control` только на `127.0.0.0/8` и
`10.0.0.0/8` отвечает контейнерам (они в `172.16.0.0/12`) `REFUSED`, Docker ждёт ~4 с и
только потом уходит на следующий сервер — резолв `api.deepinfra.com` из контейнера занимает
**4 секунды вместо 0,02**, и это платит каждый вызов pi к модели (ходы 4,8 и 11,2 с против
1,2 и 1,5 с локально). Проверка одной командой:
`docker exec icarus-user-<кто-то> getent ahostsv4 api.deepinfra.com` — должно быть ~20 мс.

Правильное лечение — на хосте (`access-control` на docker-подсеть в unbound + reload,
тогда перестают тормозить и остальные контейнеры). Но `./script/redeploy` на всякий случай
всегда прописывает контейнерам явный `docker.dns` — сейчас `1.1.1.1 8.8.8.8` (значение
приезжает в `render-config.ts` переменной `ICARUS_DNS`, а не правится руками на хосте).
Цена — имена других контейнеров и локальные зоны (`*.trousev.pro`) внутри контейнеров
резолвятся публично; когда хост починят, `ICARUS_DNS=none` (в variables environment или
в вызове скрипта) уберёт строку из `config.yaml`, и контейнеры вернутся на резолвер хоста.
То же поле есть и в `config.yaml` (`docker.dns`, см. `config.example.yaml`) — им можно
задаться и без деплоя.

## Устройство репозитория

```
script/               команды разработчика: update, test, lint, server, panel, redeploy
packages/service/     сервис: HTTP, сессии pi (сжатие и уборка), контейнеры, telegram-бот,
                      распознавание речи, панель управления
packages/extensions/  расширения pi, которые живут в контейнере пользователя
docker/user/          образ контейнера пользователя
docker/service/       образ самого icarus: node, git и клиент docker
docker-compose.yml    стек, который собирает ./script/server (в git не попадает)
specs/                спеки этапов
tools/rpc-probe.mjs   отладочный клиент к pi по RPC
tools/artifacts-mcp/  встроенный MCP артефактов (stdio): список, чтение, ссылки, проверка
tools/maple-mcp/      встроенный MCP Maple (stdio + HTTP)
```
